# Pixelgrid 1.3.0: variant system implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the single-purpose starter setup into a variant system (registry, design apply and undo with backups, one variant at a time, neutral tone labels), shipping with the IT company as the only variant, released as 1.3.0.

**Architecture:** Variants are PHP arrays in `inc/variants/{slug}.php`, read through one registry function with a filter. The setup code in `inc/starter-content.php` takes a variant slug and marks every item `{variant}:{key}`. A new `inc/starter-design.php` applies a variant's look (user global styles, header and footer parts, templates) as site-level customisations, with backups, and undoes it without losing edits made after setup.

**Tech Stack:** WordPress 7.1 block theme (theme.json v3), PHP 7.4+, WP-CLI for tests, Laragon local stack.

**Spec:** `docs/superpowers/specs/2026-11-18-variants-design.md` (sections 3, 5, 6.1, 6.2 tone labels, 6.4, 6.5 mechanism, 6.6, 7 release cadence, 8, 10)

Later plans (written after each release ships): 1.4.0 Agency, 1.5.0 News portal, 1.6.0 E-commerce.

## Global Constraints

- Block theme, theme.json version 3, `Requires at least: 6.6`, `Tested up to: 7.1`, `Requires PHP: 7.4`.
- Text domain `pixelgrid`; every user-facing string translatable; prefix `pixelgrid_` for functions and options.
- Nothing is created or changed without the user ticking options and clicking a button on Appearance > Pixelgrid setup. No external calls, no file imports.
- Admin notice: `admin_notices` only, permanently dismissible, Dashboard and Themes screens only, fresh sites only.
- Palette slugs and block style names do not change (`paper|blue|sun|night|fog|red|footer` and `is-style-tone-*`). Only labels and palette names change.
- Starter marker: post meta `_pixelgrid_starter` = `{variant}:{key}` (for example `it:page-home`). This format and the option names in Task 3 are fixed for all later releases.
- A 1.2.0 site updated to 1.3.0 must look and behave the same.
- Release zip built with `git archive`; `docs/`, `tests/`, `README.md`, `.gitattributes` excluded via `export-ignore`.

## Review Focus

1. **A 1.2.0 site with starter content updates to 1.3.0.** Old markers (`page-home`) must be read as IT, listed on the setup page, and removed cleanly. Test in Task 3.
2. **The user edited Styles before setup.** Removal must put those exact styles back, not reset to theme defaults. Test in Task 4.
3. **The user edited the header in the Site Editor after setup, then removes starter content.** Their edit must survive, and the page must say it was kept. Test in Task 4.
4. **The user trashes a starter page, then clicks Add again.** The page is recreated, not reported as already existing. Test in Task 3.
5. **The user tries a second variant while one is set up.** Nothing is created, and they see why. Test in Task 3 (function) and Task 5 (screen).

## File structure

| File | Responsibility |
|---|---|
| `inc/variants.php` (new) | Registry: list, look up and check availability of variants |
| `inc/variants/it.php` (new) | IT variant definition, absorbing `inc/starter-posts.php` and today's page and category lists |
| `inc/starter-content.php` (modify) | Create and remove content for a given variant, markers, upgrade of old markers |
| `inc/starter-design.php` (new) | Apply and undo a variant's styles, parts and templates, with backups |
| `inc/starter-screen.php` (new) | Setup page markup, form handler, notice (moved out of `starter-content.php`) |
| `functions.php` (modify) | Neutral tone labels; load the new files |
| `theme.json` (modify) | Palette names use the neutral labels |
| `tests/` (new) | WP-CLI test scripts, runner and test-site script |

`inc/starter-posts.php` is deleted; its content moves into `inc/variants/it.php`.

### Task 3: Variant-aware starter content, markers and upgrade

**Files:**
- Modify: `inc/starter-content.php`
- Create: `tests/test-starter.php`

**Interfaces:**
- Consumes: Task 2 registry.
- Produces:
  - `pixelgrid_starter_key( string $variant, string $key ): string` returns `"$variant:$key"`.
  - `pixelgrid_starter_find( string $post_type, string $full_key ): int` keeps today's statuses, which exclude trash.
  - `pixelgrid_starter_active_variant(): string`, from option `pixelgrid_starter_variant`. Returns `''` when none.
  - `pixelgrid_starter_create( string $variant, array $options ): array|WP_Error`.
    - Options keys: `design, pages, posts, menu, reading` (bools).
    - Returns `array( 'pages' => int, 'posts' => int, 'menu' => int )`.
    - Errors: `pixelgrid_variant_unknown`, `pixelgrid_variant_unavailable`, and `pixelgrid_variant_busy` when another variant is active.
    - Calls `pixelgrid_design_apply()` (Task 4) when `design` is set.
  - `pixelgrid_starter_remove(): array`. Returns `array( 'removed' => int, 'styles_restored' => bool, 'kept' => string[] )` and calls `pixelgrid_design_undo()`.
  - `pixelgrid_starter_upgrade(): void`, hooked to `admin_init`. Runs once when option `pixelgrid_starter_schema` < 2:
    - rewrites old markers to `it:` form
    - sets `pixelgrid_starter_variant = 'it'` if any starter content exists
    - sets schema to 2
- Options kept from 1.2.0: `pixelgrid_starter_terms`, `pixelgrid_starter_reading`, `pixelgrid_starter_done`.
- Page, front and menu come from the variant array, not hardcoded slugs. `pixelgrid_starter_fix_links()` is unchanged.

### Task 4: Design apply and undo with backups

**Files:**
- Create: `inc/starter-design.php`, `tests/test-design.php`, `tests/fixtures/test-style.json` (a minimal v3 style variation whose palette sets `blue-hover` to `#00C2A8`)
- Modify: `functions.php` (require it), `inc/starter-content.php` (remove the `function_exists` guard)

**Interfaces:**
- Consumes: Task 2 variant arrays (`style`, `parts`, `templates`).
- Produces:
  - `pixelgrid_design_apply( array $variant ): void`
  - `pixelgrid_design_undo(): array`, returning `array( 'styles_restored' => bool, 'kept' => string[] )`. `kept` lists entity labels like `header` that were left because they changed after setup.
  - Both read and write option `pixelgrid_starter_design`:
    ```
    array(
      'styles_before'  => string,
      'styles_written' => string,
      'entities'       => list of array(
        'type'      => 'wp_template_part' | 'wp_template',
        'slug'      => string,
        'post_id'   => int,
        'created'   => bool,
        'before'    => string,
        'written'   => string,
      ),
    )
    ```
- Styles:
  - The user global styles post comes from `WP_Theme_JSON_Resolver::get_user_data_from_wp_global_styles( wp_get_theme(), true )`.
  - Applying writes the variant's style variation JSON. An empty `style` writes `{"version":3,"isGlobalStylesUserThemeJSON":true}`, which means theme default.
  - Undo restores `styles_before` only when the current content equals `styles_written`.
- Parts and templates:
  - For each entry, find an existing customisation with `get_block_template( 'pixelgrid//' . $slug, $type )`, where `source === 'custom'` and `wp_id` is set.
  - If one exists, store its content as `before` and update it. If not, insert a post of `$type` with `post_name = $slug`, term `pixelgrid` in `wp_theme`, and for parts, term `header` or `footer` in `wp_template_part_area`. Mark it with `_pixelgrid_starter`.
  - The content is the referenced pattern's markup, expanded with `pixelgrid_starter_expand()`.
  - Undo: if the current content still equals `written`, either delete the post (when created) or put `before` back. Otherwise add the slug to `kept`.

- [ ] **Step 1: Write `tests/test-design.php`.** It uses a fake variant through the filter: `style 'tests/fixtures/test-style.json'` (theme-relative, read with `get_parent_theme_file_path()`), `parts array( 'header' => 'pixelgrid/footer' )` and `templates array( 'home' => 'pixelgrid/blog-heading' )`. Cases:
  - **Clean site.** Apply, then the header renders the footer pattern, and the user styles post contains the fixture's palette. Undo returns `styles_restored` true and `kept` empty, the custom header post is gone, and the styles equal the original.
  - **User styles before setup (Review Focus 2).** Set user styles to a custom palette first, apply, undo. The styles equal that custom palette exactly.
  - **Header customised before setup.** Create a custom header with content `X`, apply, undo. The header content is `X` again.
  - **Header edited after setup (Review Focus 3).** Apply, edit the custom header content to `Y`, undo. Header content stays `Y` and `kept === array( 'header' )`.
  - **Styles edited after setup.** Apply, change the user styles, undo. `styles_restored` is false and the change remains.
